# Patches/Core/ — Core例外パッチ台帳

このディレクトリは、`CLAUDE.md`「Core File Modification Policy」の★狭い例外
(2026-07-30追加、D-6/P465振り返り + Fable5クロス監査。2026-08-16、Class B追加、
P602/D-57振り返り + Fable5クロス監査 + ユーザー明示承認)に基づき提案された、
`Core/px68k/`・`Core/c68k/`向けパッチファイルのみを置く。

**重要: このディレクトリのパッチはAIエージェントが自動適用することはない。**
`Core/`へのEdit/Writeは`PreToolUse`フックで常時ブロックされており、フックに
例外トークンや一時無効化の仕組みは存在しない(意図的——CLAUDE.mdの
「Workaround-Twiceルール」参照)。**適用は必ずユーザー自身が
手動で`git apply Patches/Core/pXXX_....patch`を実行する。**

## パッチの2分類

- **Class A**: 参照実装からの実証済み修正のverbatim移植。
- **Class B**(2026-08-16追加): 参照実装のいずれにも修正が存在しない
  (共有の上流欠陥等)場合、実機仕様書を一次情報源とし、実行時ログで
  機構そのもの(症状だけでなく)を確認した上での修正。Class Aより
  高い証拠バーを課す代わりに、参照実装への依存を外す。頻度トリップワイヤは
  両クラス合算でカウントする。

## 適用条件(要約、詳細はCLAUDE.md本体)

1. Class Aは**実証済み修正のverbatim移植のみ**。Class Bは上記4条件
   (機構の実行時確認・一次資料引用・修正不在調査・Bridge代替検討)を
   全て満たすこと——いずれの分類も新規診断のみに基づく独自修正
   (Class Bの4条件を満たさないもの)は対象外。
2. 対象範囲の全diffを添付(2行だけの切り出しは不可)。
3. サイクル途中の「レスキュー」としての提案は不可——新規Fix Planの
   冒頭からのみ。
4. パッチの効果そのものをhands-on確認することがマージ(適用)前提条件。
   効かなければ適用しない。
5. 効果確認後、置き換え対象だったBridge側近似コードは同一/直後サイクルで
   撤去する(重ね着禁止)。
6. `c68k/`・CPU実行/タイミングに関わるCore編集は、通常のCode Reviewに
   加えてCodex/Fable5のクロスファミリーレビューを必須とする。
7. **Class Bという分類自体の採否は、個別パッチの承認とは別に、
   ユーザーへ明示的・単独の質問として提示すること**——「このパッチを
   承認しますか」に紛れ込ませて分類の新設を黙認させてはならない
   (自己承認リスク、2026-08-16のP602サイクルでハーネス自体が検出)。

## ★台帳の状態欄の記入規律(恒久ルール、P686で成文化・ユーザー承認済み)

**台帳の状態欄は、そのパッチを含むサイクルの Step 6 コミット時点の事実を書く。
パッチ作成時点の「未適用」のまま放置してはならない。Build & Test Agent は
`git diff -- Core/` の検証(ポリシー条件7)を行う際、同時に台帳の状態欄が
実態と一致しているかを確認する。**

背景: 同一の乖離が **3 回**発生している(`p641`・`p657` の 2 件を P671 が是正 →
その P671 自身の行が P686 まで「未適用」のまま放置されていた)。構造的原因は
**「パッチファイルを書いた時点」と「ユーザーが `git apply` した時点」の間に
台帳を更新する担当者が居ない**こと — パッチ作成者はまだ適用されていないので
「未適用」と書くのが正しく、適用したユーザーは台帳を触らない、という担当の空白である。
Step 6 のコミットは hands-on 確認の完了後に 1 回だけ打たれるため、その時点で
「適用済み(日付、main=ハッシュ)」を書けば「未適用 → 適用済み」の 2 段階更新は
そもそも発生しない。

## 頻度トリップワイヤ

1フェーズあたりパッチ3件超(Class A/B合算)、またはBridge側検討より先に
第一候補として提案された場合は、本ポリシー自体の再審査を行う。
